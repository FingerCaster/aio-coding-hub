# 自定义余额查询与路由恢复集成

## Goal

让不具备内置余额协议的 API Key 供应商可以通过受约束的本地 JavaScript 查询并归一化账户用量；在用户显式开启余额路由门控后，已确认余额不足或账户过期的供应商不调用上游、以 `skipped` 形式保留在路由审计中，并在余额恢复后通过现有优先级和 Session 回切机制重新获得流量。

## Background

- 当前账户用量支持内置 sub2api 与 NewAPI 契约，并被定义为纯展示能力；查询结果尚不参与供应商选择、熔断或回切。
- KNaiFen 提交 `c75150897145420d630f9927519493f154032227` 提供了经过资源、网络、确认和可移植性约束的本地 JavaScript 账户用量适配器。该提交不能原样合并，但核心账户用量文件与当前代码同源，适合选择性移植并适配当前主线。
- 当前网关已在共同发送前门控点处理 OAuth 配额和本地消费上限。门控拒绝会生成稳定的 `skipped` attempt、零上游调用，并且不消耗 Ready Provider 尝试额度。
- 当前回切机制维护路由优先级、Provider 级恢复信号、Session 绑定和发送前复检。余额恢复必须加入这套机制，不能建立第二套供应商排序或直接篡改熔断状态。
- 用户已明确选择保留余额门控的 `skipped` 路由审计，而不是在 Provider resolution 阶段静默过滤候选。

## Deliverables

1. **自定义 JavaScript 账户用量查询**：选择性移植自定义脚本适配器、安全边界、草稿测试、配置界面与测试，并让结果进入后端拥有的共享账户用量快照。
2. **余额门控与恢复回切**：增加默认关闭的显式路由门控，复用共同发送前门控与现有回切机制，覆盖未配置、阻断、恢复、并发和 Session 场景。

第二个交付依赖第一个交付提供稳定、后端可读且带新鲜度的账户用量快照；两个交付分别实现、验证和提交，父任务负责最终跨层验收。

## Requirements

### R1. 自定义查询能力

- 仅直接 API Key 供应商可以选择自定义 JavaScript 适配器；OAuth 供应商不得向脚本暴露 OAuth 凭据。
- 脚本必须在独立、资源受限的运行环境执行，不具备文件、进程、环境变量、Tauri IPC 或任意网络能力。
- 脚本只负责生成一个受限 HTTP 请求计划并解析一个有界 JSON 响应；真实请求由 Rust 校验并执行。
- 只允许用户确认过的 HTTPS Origin，禁止重定向，并限制脚本、请求、响应、输出、执行时间、并发量及文本字段大小。
- 启用、测试或改变脚本/Origin/Base URL 信任边界时必须经过后端拥有的原生确认；取消确认不得读取 API Key 或发送请求。
- 自定义脚本、Origin 和确认状态保持本机私有；分享、完整导出和导入不得自动携带或启用脚本。
- 不提供“仅携带源码但禁用”的便携形式；任何导出/备份均彻底移除自定义源码与 Origin，换机或恢复后必须在目标机器重新配置并原生确认。
- 查询结果必须归一化到现有 `ProviderAccountUsageResult`，并继续支持余额、套餐剩余、周期额度、过期时间和稳定状态。

### R2. 显式路由门控

- 余额影响路由必须是独立、显式、默认关闭的 Provider 配置；启用余额展示不等于启用路由门控。
- 同一门控能力统一适用于 `sub2api`、NewAPI billing、NewAPI account 和自定义 JavaScript 适配器，使用共享归一化状态；不得按适配器种类产生不同的路由语义。
- 未配置账户用量、适配器关闭、供应商不支持余额查询，或路由门控关闭时，供应商资格与当前行为完全一致，不发起为路由服务的余额刷新。
- 只有符合已确认新鲜度和可信状态规则的 `zero_balance` 或 `expired` 快照可以阻止发送。
- 被余额门控的 Provider 在共同发送前门控点产生 `skipped` attempt，零上游调用、不消耗 Ready Provider 尝试额度、不计为供应商失败，也不得打开或重置熔断。
- `skipped` 可见性以 Provider 本次确实被现有 planner/route 计划并进入共同 gate 为前提；不得为了每个稳态请求重复展示余额阻断而额外制造 Direct target 或合成 attempt。
- 跳过原因必须有稳定的结构化 reason code，能够与电路打开、冷却、OAuth 配额及本地消费上限区分。
- 如果同时存在现金余额和套餐剩余，只要任一可消费额度为正，就不得因另一项为零而阻断。
- `zero_balance` 与正可消费额度矛盾、`expired` 与未来过期时间矛盾时必须 fail-open，且不得把矛盾结果当作确认恢复。
- 余额快照不提供权威恢复时间；后台下次刷新时间不得被当成 `Retry-After`。混合门控只能沿用其他 gate 已有的可信恢复时间。
- 任何终态只要包含余额 `skipped`，都不得写入现有 recent-error 503 缓存；即使混合门控响应保留其他 gate 的可信 `Retry-After`，余额恢复、失败或过期后的下一请求也必须重新进入 Provider 选择。

### R3. 刷新与恢复

- 路由门控使用后端拥有的 Provider 级共享快照，不依赖供应商页面或 React 组件是否打开。
- 网关请求路径不得同步执行 JavaScript 或等待远端余额接口；刷新必须发生在有界后台运行时。
- 启用余额路由门控即建立持续的 Gateway 消费租约，忽略纯展示的 `timedRefreshEnabled` 开关，并始终按该 Provider 已保存的 `60–300` 秒刷新间隔查询；不增加另一套恢复轮询配置，也不在阻断时强制固定 60 秒。
- 路由门控只信任年龄严格小于 `2 × refreshIntervalSeconds` 的成功快照，即新鲜度范围为 `120–600` 秒；展示层可继续使用独立的 60 分钟缓存寿命，二者不得混用。
- 快照缺失、超过路由新鲜度上限，或刷新返回 `query_failed`、`auth_failed`、`configuration_required` 时必须 fail-open：立即恢复路由资格并继续后台重试，不得沿用旧的余额阻断。
- 余额阻断期间仍按受控计划刷新。只有同一有效配置 generation 的新鲜成功结果明确从阻断变为 `available` 时，才发布 Provider 级、可被多个 Session 独立观察的恢复代次，不能使用一次性全局布尔标记。
- 同 generation 的查询失败或快照过期可保留“上次确认阻断”的转换记忆，但实际 gate 必须立即 fail-open；后续新鲜 `available` 才能据此发布一次恢复代次。
- 因快照缺失、过期或查询失败而 fail-open 时只解除发送门控：新 Session 和普通 fallback 可以使用该 Provider，但不得发布主动回切恢复代次；现有 Session 等待后续确认恢复或既有独立回切触发。
- 恢复后的高优先级 Provider 按现有路由顺序进入回切规划，并在实际发送前再次经过余额、熔断、冷却和其他 Provider limit 门控。
- 回切尝试成功后复用现有单调 Session 绑定提交；失败或再次被余额门控时继续现有 fallback，不伪造探针成功或熔断恢复。
- 再次确认阻断必须立即撤销该 Provider 尚未被 Session 观察的旧余额恢复代次。配置修改、脚本权限变化、Provider 删除和运行时失效必须使旧快照/旧恢复代次失效，旧异步结果不得恢复或阻断新配置。
- 查询语义、凭据身份、刷新间隔或 gate 资格变化才重置对应 generation/恢复状态；Provider name/note 与纯展示 `timedRefreshEnabled` 变化不得误丢阻断转换记忆。完整配置导入成功提交后必须同步 reset 账户运行时、live Session、相关 recent errors 并立即收敛 Gateway targets，不能等待后台心跳。

### R4. 兼容与安全

- 不改变默认路由顺序、forced provider、managed model、重试预算、流式提交边界或现有 OAuth/消费限额语义。
- “余额影响路由”开关在完整配置备份/恢复和本机 Provider 复制中保留；单 Provider 分享/导入必须重置为关闭。自定义 JS 因适配器内容不便携，任何导入后适配器与门控均保持关闭。
- 本机复制自定义 Provider 可保留脚本草稿与门控偏好，但新 Provider 身份不得继承脚本确认。源 custom 已启用时复制前必须为新身份重新原生确认，取消则不创建副本；未确认的 custom 不执行 Gateway 刷新或门控。
- 用户显式关闭正在生效的余额门控或对应适配器后，下一请求必须按最新配置重新选择，而不是让旧 Session 绑定无限停留在 fallback；该行为不得伪造余额或熔断恢复代次。
- 现有 `GW_ALL_PROVIDERS_UNAVAILABLE` 和 denied Provider 审计规则保持兼容；余额门控不得静默改写为“无启用供应商”。
- API Key、脚本源、允许 Origin、上游响应、真实余额和个人字段不得进入普通日志、IPC 错误、路由 attempt、生成绑定或测试夹具。
- 所有测试使用合成凭据、保留测试域名和合成金额。

## Acceptance Criteria

- [x] 自定义 JavaScript 适配器能在确认后完成一次受限请求并返回现有账户用量 DTO；超时、越权 Origin、重定向、超限、非法输出和确认竞态全部失败关闭且不泄密。
- [x] 自定义配置变更撤销旧确认；分享、导出和导入不会携带或自动启用脚本。
- [x] 完整配置备份也不保留禁用脚本副本；导入载荷即使手工注入自定义字段也会被剔除。
- [x] 未配置/未开启余额查询及未开启路由门控的 Provider，其选择、发送、Session 和回切行为与当前主线一致。
- [x] 四种账户用量查询路径在相同归一化状态下得到相同门控结果，且都要求逐 Provider 显式开启。
- [x] 新鲜 `zero_balance` / `expired` Provider 产生结构化 `skipped` 路由记录、零上游调用、零 Ready 尝试消耗且不改变熔断。
- [x] 已知阻断的高优先级 Provider 不被人为加入每个稳态请求；一旦被现有路由/回切计划实际检查，余额拒绝必须以普通 `skipped` 可见。
- [x] 现金余额为零但套餐剩余为正时仍可路由；两类可消费额度均耗尽时才阻断。
- [x] 矛盾的 `zero_balance + positive amount` 或 `expired + future expiry` fail-open 且不发布恢复代次。
- [x] 被阻断 Provider 在无 UI 消费者时仍能受控刷新；恢复后下一次符合条件的请求按原优先级尝试并在成功后完成 Session 回切。
- [x] 开启路由门控后，即使关闭展示定时刷新也按已配置的 `60–300` 秒间隔持续刷新；关闭路由门控后不再为 Gateway 保持刷新租约。
- [x] 路由快照达到 `2 × refreshIntervalSeconds` 时立即视为过期并 fail-open；展示缓存寿命不会延长路由阻断。
- [x] 快照缺失、过期、查询失败、认证失败或配置不完整时 fail-open；旧阻断不会在无可信证据时继续锁住 Provider。
- [x] fail-open 解除门控但不触发主动 Session 回切；只有新鲜成功的 `available` 转换发布恢复代次。
- [x] 阻断后的查询失败/快照过期不延续 gate；其后的新鲜 `available` 仍能发布一次恢复，而再次确认阻断会撤销旧恢复信号。
- [x] 多 Session 能各自观察同一恢复代次；并发旧请求不能覆盖较新的回切绑定。
- [x] 恢复信号产生后、发送前再次变为余额不足时，Provider 再次以 `skipped` 结束且请求继续 fallback。
- [x] 全部余额门控、余额门控与熔断混合、forced provider、managed model、非流与流式路径均有回归测试。
- [x] 前端、生成绑定、Rust 单元/集成测试、类型检查、lint、格式检查及敏感信息差异审计全部通过。
- [x] 完整备份和本机复制保留原生适配器的门控开关；单 Provider 分享导入重置开关；自定义适配器导入后保持无脚本且门控关闭。
- [x] 纯余额阻断不携带以刷新计划伪造的 `Retry-After`；与 circuit/limit 混合时只投影其他 gate 的可信时间。
- [x] 余额与 circuit/limit 混合阻断可以返回其他 gate 的 `Retry-After`，但不写 recent-error cache；余额恢复或 fail-open 后的下一请求会重新选择并复检。
- [x] 显式关闭余额门控后，旧 fallback Session 在下一请求按当前路由重新选择，且余额/circuit recovery epoch 均不因此增加。

## Out of Scope

- 让自定义脚本修改网关请求或响应。
- 根据余额自动修改 Provider 的启用状态、排序或路由配置。
- 将余额不足静默预过滤为完全不可见的候选。
- 将账户查询失败等同于模型请求必然失败。
- 支持 Cookie、网页登录、DOM 抓取或任意多请求脚本工作流。
