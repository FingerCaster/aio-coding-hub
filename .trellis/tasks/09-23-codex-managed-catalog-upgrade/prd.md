# Codex 更新后升级受管模型目录

## Goal

Codex CLI 更新后，用户能把 AIO 受管的 `model_catalog_json` 重新同步到当前基础目录，并继续套用已启用的模型上下文规则和受管 Profile 的模型元数据。新启动的 Codex 会话读到新目录；更新前已经打开的会话不热更新。

## Background

上下文规则和受管 Profile 都不修改 Codex 安装文件。任一启用规则或任一受管 Profile 存在时，AIO 生成完整合并目录，并把根 `model_catalog_json` 指到应用数据目录中的 `cli-proxy/codex/managed-model-catalog.json`。Codex 因此使用这份静态目录，不再合并安装包里的新模型。两者都没有时，恢复用户原来的绑定或缺失状态，并只删除 AIO 拥有的生成文件。

基础来源保持现有所有权：原始根配置有绝对用户 `model_catalog_json` 时，以该文件全文为底；否则运行当前安装的 Codex `debug models --bundled`。基础模型、未知字段和顶层字段原样保留，再写规则投影，并追加 `aio/<profile_name_key>`。`aio/*` 的 reasoning、默认 effort 和上下文只来自 Provider 模型能力。

已启用规则必须恰好命中一个基础 slug，且该条目的 `context_window` 与 `max_context_window` 都是非负 JSON 整数。现在的自动对账在可执行文件指纹、规则、Profile 集合或 owner 元数据变化时重建；指纹不含 bundled 内容哈希。启动对账失败会停在 `ReadingSettings`，应用进入可重试的降级状态，已有横幅能打开 Codex 页。失败时保留上一份有效生成目录、启用意图和代理备份，不会静默停用规则。

## Requirements

- R1. 升级复用现有受管目录事务：Profile 生命周期锁、owner metadata、哈希、原子写入和失败回滚。不另写绕过所有权的目录，不修改 Codex 安装文件。
- R2. 没有用户目录时，手动升级强制重新运行当前 Codex 的 `debug models --bundled` 并重建，即使可执行文件指纹没变。有绝对用户目录时，强制重读该文件的当前内容，不改用 bundled。
- R3. 重建结果重新套用当前仍启用的上下文规则和当前受管 Profile 的模型元数据。不把旧基础模型原样留在新目录里。
- R4. 普通升级不改规则集合、Provider 模型能力或受管 Profile。无法套用的规则使本次升级在第一次写盘前失败，并列出全部可修复的无效规则。
- R5. 可修复的无效规则只包括：目标 slug 不在基础目录中，或目标的两个上下文字段不是非负整数。用户明确选择「禁用无效规则并升级」，且提交的模型 ID 集合与当前无效集合完全一致时，才把这些规则设为 `enabled: false`，保留 `model_id` 和 `context_window`，然后用剩余启用规则重建。
- R6. 基础目录本身无效、slug 重复、`aio/*` 别名冲突、Codex 不可用，以及其他非规则目标错误，不提供也不接受「禁用无效规则并升级」。
- R7. 保留现有自动对账。启动、目录读取、规则或能力保存、配置保存和代理启停仍按指纹与 owner 对账，不因为手动升级的存在而每次强制重跑 bundled。自动对账遇到无效规则时继续失败关闭，不自动停用规则。
- R8. 自动对账失败后应用保持现有启动降级。Codex 页展示无效规则和「禁用无效规则并升级」。确认成功后仍由用户使用现有「重试启动」。不在启动阶段弹选择框。
- R9. 没有启用规则且没有受管 Profile 时，升级不安装新的受管目录。禁用后两类所有者都消失时，恢复原始 `model_catalog_json` 绑定或缺失状态，并删除 AIO 拥有的生成文件。
- R10. 成功只对新启动的 Codex 会话生效。界面必须说明这一点，不得重启或改写已经运行的 Codex 进程。

## Acceptance Criteria

- AC1. 没有用户目录、bundled 内容已变化但可执行文件指纹不变时，手动升级写出入新 bundled 内容、当前启用规则和当前 `aio/*` 元数据的受管目录。指纹不变的自动对账不写这份新内容。
- AC2. 原始基础是绝对用户目录时，升级使用该文件的当前字节。用户文件独有的模型和非目标字段仍在；实现不调用 `debug models --bundled`。
- AC3. 一条或多条启用规则缺失，或目标上下文字段不是非负整数时，普通升级不写目录、配置、备份、规则、能力或 Profile，并返回全部这些规则的模型 ID 和原因。上一份有效受管目录保持不变。
- AC4. 「禁用无效规则并升级」只在模型 ID 集合与 AC3 的当前集合完全一致时写盘。这些规则变为停用且保留原 token 值；其余启用规则和 Profile 元数据进入新目录。集合不一致时不写任何文件或设置。
- AC5. 基础 JSON 无效、slug 重复、别名冲突或 Codex 不可用时，升级失败且没有禁用入口；规则保持原状。
- AC6. 启动对账遇到 AC3 的规则目标错误时，仍在 `ReadingSettings` 失败，保留启用规则和上一份有效目录，不进入后续启动阶段。Codex 页能列出这些规则并完成 AC4。成功后现有「重试启动」仍是继续启动的入口。
- AC7. 没有启用规则且没有受管 Profile 时，升级不创建受管目录。AC4 之后两类所有者都为空时，根绑定恢复为原来的用户路径或缺失状态，AIO 生成文件被删除。
- AC8. 升级成功后的界面说明需要新启动 Codex 会话。测试不要求、实现也不启动外部 Codex 会话。

## Out of Scope

- 不修改 Codex 远端 `/models` 动态目录，也不把用户目录替换成 bundled。
- 不自动增删规则，不改 Provider 模型的 reasoning、默认 effort 或上下文元数据。
- 不让用户从无效集合里挑一部分禁用；要么整组确认，要么不写。
- 不热更新已打开的 Codex 会话，不代用户重试启动。
- 不安装、替换或检测 Codex 可执行文件的发布过程。
