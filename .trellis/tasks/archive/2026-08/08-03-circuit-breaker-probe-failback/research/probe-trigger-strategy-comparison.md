# 试探触发策略比较

> 本文前半部分保留最初方案比较时的基线假设；其中“只等 `open_until`”“半开累计 3 次成功”和“自然模式可能永久不试探”均已被后续产品决定取代。实施以文末“最终收敛结论”以及任务 `prd.md` / `design.md` 为准。

## 问题本质

当前熔断器虽然有 `HALF_OPEN`，但 `OPEN` 到期只是“具备被试探的资格”，并不代表供应商已经恢复。系统必须决定由哪一类请求取得试探权，并用什么结果把供应商从 `HALF_OPEN` 推进到 `CLOSED` 或退回 `OPEN`。

回切策略与试探策略是两个独立维度：

- **试探策略**回答“如何证明供应商恢复”。
- **回切策略**回答“证明恢复后，已有会话何时改用更靠前的供应商”。

## 方案 A：真实业务请求单飞试探（推荐）

### 建议时序

```text
OPEN（未到期）
  -> 所有请求跳过该供应商
OPEN（已到期）
  -> 第一个满足路由条件的请求原子取得 probe lease
  -> HALF_OPEN / probe_in_flight
     -> 其他并发请求不能同时试探，继续使用当前稳定供应商
     -> 试探请求按真实模型、协议、鉴权和响应路径发送
        -> 成功：累计恢复成功；满足恢复阈值后 CLOSED
        -> 失败：立即 OPEN，重置 open_until；同一用户请求继续故障转移
```

### 与自然回切的关系

- 已绑定低优先级供应商的会话继续优先复用该供应商，不主动抢占 probe lease。
- 新会话或原有路由自然触达高优先级供应商时，才可能成为试探请求。
- 如果系统长期只有已有黏性会话且低优先级供应商持续成功，高优先级供应商可能长期不被试探；这是“自然回切”的预期代价。

### 与积极回切的关系

- 同一会话的下一轮请求在应用会话黏性前，检查当前稳定供应商之前是否存在更高优先级候选。
- 候选为 `CLOSED` 时可直接回切；候选为已到期且可试探状态时，该请求尝试取得 probe lease。
- 取得 lease 的请求成功后可完成或推进恢复并回切；失败时重新熔断，高优先级请求尝试不得覆盖原有稳定绑定，当前用户请求继续回退到稳定供应商。
- 未取得 lease 的并发请求继续走稳定供应商，避免恢复瞬间流量齐射。

### 优点

- 验证真实请求路径，包括模型映射、协议桥接、OAuth/API Key、流式响应和响应语义。
- 不需要后台调度器，不产生空闲期探测流量和额外的固定探测成本。
- 成功/失败可以沿用现有 gateway 失败分类、attempt/route 日志和 circuit 记录路径。
- 失败时可使用现有 failover 返回稳定供应商，用户通常只承担额外失败尝试的延迟。

### 风险与待定项

- 失败试探会增加该轮响应延迟；需要决定试探是否只允许一次上游尝试，还是允许供应商配置的重试策略。
- 当前半开要求 3 次成功。若保留该阈值，需要明确第一次/第二次成功后是否更新会话绑定，以及如何连续获得后续试探机会。
- 请求可能包含用户真实内容；虽然这是正常路由范围，但意味着“试探”不是无副作用健康检查。
- probe lease 必须有 generation/过期机制；请求取消、进程异常或流未完成时不能永久卡住半开状态。

## 方案 B：后台主动探测

### 建议时序

```text
OPEN 到期
  -> 后台调度器取得 probe lease
  -> 构造供应商类型对应的最小探测请求
     -> 成功：累计恢复成功；满足阈值后 CLOSED
     -> 失败：重新 OPEN 并退避
用户下一轮请求
  -> 只在供应商已 CLOSED 时执行积极回切
```

### 优点

- 用户请求不会承担首次试探失败的额外延迟。
- 积极回切时供应商已经通过独立恢复判定，语义最贴近“已经正常再切换”。
- 即使没有新会话，供应商也能按时间自动恢复。

### 风险与新增复杂度

- 每个 CLI、桥接类型、模型映射和鉴权方式都需要构造有效探测；探测成功不一定代表用户真实模型可用。
- 会产生真实上游请求、token 用量和潜在费用；大量 provider 同时到期时需要全局与逐 provider 限流。
- 必须处理应用休眠/重启、调度漂移、OAuth 刷新、429/配额、超时、网络错误和重复任务。
- 现有手动 Provider 可用性测试把 400、404、429 视为“可用”，不能直接用于关闭熔断；自动恢复需要更严格且与 gateway 一致的成功定义。
- 后台探测是否写入普通请求日志、用量统计和告警需要新增可观察性契约，避免制造用户没有发起的“对话请求”。

## 方案 C：混合策略（不建议首期）

- 默认真实请求单飞试探；仅在显式开启时后台预热。
- 可以兼顾低延迟积极回切与低复杂度默认行为，但会增加配置组合、状态竞争和测试矩阵。
- 首期没有基础事实要求同时实现两种探测机制，因此建议先排除。

## 推荐结论

首期采用**真实业务请求单飞试探**，原因是它复用现有 gateway 的真实成功语义、故障转移和日志链路，新增机制主要集中在 circuit probe lease 与 provider 排序，不必另建一套可能与真实请求漂移的健康检查系统。

## 最终收敛结论

- 单飞试探不能只依赖新会话自然触达，也不能受自然/积极回切策略控制。
- 即使当前所有会话都已绑定到低优先级稳定供应商，高优先级熔断供应商到达可试探时间后，也必须从后续真实业务流量中取得一次试探机会；否则会话黏性会让它永久无法解除熔断。
- 因此请求排序应先处理“是否存在当前请求可认领的到期 probe lease”，再处理普通会话复用 preference。只有一个请求临时把待试探 provider 放到稳定绑定之前；其余请求维持原有排序。
- 试探成功与“是否把已有会话绑定切回”必须分开提交：前者更新 circuit recovery，后者由自然/积极回切策略决定。
- 现有默认 30 分钟 `open_until` 不能充当首次试探等待时间，试探节奏需要独立控制。
- 自然回切拟以当前会话发生上下文压缩后的下一轮请求为试探/回切边界，以兼顾提示缓存复用和较低试探频率。
- 积极回切在当前会话的每一轮新请求检查更高优先级 provider；“下一轮”不是新建对话。
- 首次及失败后的最短 probe 间隔复用 `provider_cooldown_seconds`，默认 30 秒；自然模式另有 provider 全局 300 秒最大等待，压缩可提前触发。
- 自然模式的压缩触发在一次真实 dispatch 后消费；失败后等待新压缩或新一轮 300 秒兜底，不按 30 秒连续追试。
- 一次完整成功即恢复，不再累计 3 次；随后进入 5 分钟恢复观察期，期间一次 counted failure 立即重新打开。
- 已有会话每轮用当前 CLI 最新路由判断高优先级；管理员改动路由是下一轮显式触发。
- 策略为全局设置，默认自然；积极模式每轮检查，自然模式按压缩/兜底检查。
