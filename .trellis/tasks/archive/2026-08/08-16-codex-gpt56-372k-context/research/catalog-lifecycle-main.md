# Research: origin/main Codex catalog lifecycle and 372K transaction boundary

> 2026-08-17 最终产品决策：跟随 Codex 上游 `272000` 的十进制目录口径，372K 的实现与验收值为 `372000`。下文关于 `380928` / `372 * 1024` 的数值建议属于已被覆盖的历史分析，不得作为实现要求。

- Query: 基于固定的 `origin/main`，确认现有 Codex managed catalog 的生成、绑定、代理 baseline、设置事务和回滚链路，并给出满足 GPT-5.6 372K 专属开关所需的最小安全生命周期设计与测试矩阵。
- Scope: mixed
- Date: 2026-08-17

## Findings

### 1. 结论摘要

1. 当前实现不能通过给 `generate_catalog` 增加三处字段替换来满足任务。`prepare_for_profiles` 同时把“代理已启用且已应用”和“profiles 非空”当作 catalog 存在前提；而 PRD 要求 catalog 需求为 `has_managed_profiles || gpt56_372k_enabled`，并且代理关闭时也必须有效。
2. 372K 应作为完整 catalog 的第二种派生策略。唯一值为 `372 * 1024 = 380928`；开启时只对 `gpt-5.6-sol`、`gpt-5.6-terra`、`gpt-5.6-luna` 的 `context_window` 和 `max_context_window` 同时写 `380928`。不得写顶层 `model_context_window`、`model_auto_compact_token_limit`，不得改 `effective_context_window_percent`，也不得影响 `aio/*` entries。
3. 代理关闭支持的真正难点是原始 `model_catalog_json` binding 的所有权。目前原路径只隐含在 proxy backup 中，owner metadata 并不保存它；一旦 direct config 已绑定 AIO catalog，再启用代理会把 AIO 路径备份为 baseline，现有“污染修复”只能删除该 key，无法恢复用户原 catalog 路径。
4. 新 owner schema 必须显式记录并校验原始 binding（用户绝对路径或 bundled/absence）、策略输入、精确目标值和 profile 集合。停用时必须先恢复所有 config/baseline binding，最后才删除 generated catalog；这样 generated metadata 可兼作崩溃恢复记录。若实现仍坚持先删 generated，就必须另建持久 ownership journal，否则无法满足恢复要求。
5. 开关必须有专属事务入口。普通 settings writer 不拥有该字段；专属入口应在 profile lifecycle lock 下先完整 prepare，再条件提交 settings intent，再方向感知地 apply 文件计划。任何一步失败都只回滚仍等于本事务 after-state 的资源，并重新收敛到最终 canonical settings。
6. 不应复用广义 `cli_proxy::sync_enabled` 作为专属开关的提交路径。该函数逐 CLI 返回成功/失败 rows，`settings_service` 会把 partial failure 和顶层错误都压成 `Ok(false)`，不会触发 settings rollback；这会产生“开关已持久化为 true，但目录仍是 272000”的假成功状态。
7. 应用启动、代理启停/退出恢复、profile 增删、provider capability 更新、Codex home rebind、CLI fingerprint 变化都必须调用同一个 canonical reconciler。OAuth-only 模式切换只应保留 active binding，不应因为无关设置变化重新抓取 catalog。

### 2. 调研基线

- 仓库基线固定为 `FingerCaster/aio-coding-hub` 的 `origin/main` commit `d02728cea0990c0fc019c9c8c6bfa67796a0295b`（2026-08-15，`chore(tasks): archive beta.8 integration work (#41)`）。本报告的业务代码行号均对应这一固定版本，而不是把当前任务改动当成事实来源。
- OpenAI Codex 基线固定为 tag `rust-v0.147.0`、commit `be6e8eac029b183056b7e4402879f15d2c85f61b`。
- 0.147.0 的 bundled `models.json` 中，三个目标 slug 的 `context_window` 和 `max_context_window` 都是 `272000`：Sol 位于 `models.json:4,27-28`，Terra 位于 `:119,142-143`，Luna 位于 `:232,255-256`。
- 该 JSON 没有显式 `effective_context_window_percent`。同版本协议默认值为 95，模型 fallback 也是 `272_000 / 272_000 / 95`，运行时按 `context_window * percent / 100` 计算有效窗口。因此名义 `380928` 对应有效值 `361881`；本任务明确保留这一上游语义。

### 3. 当前 catalog 状态机

#### 3.1 生成前提被代理和 profiles 双重锁死

`prepare_for_profiles` 先校验 profiles，然后必须取得 enabled proxy baseline；没有 baseline 直接返回 inactive，代理配置未实际应用则报 drift（`src-tauri/src/infra/codex_model_catalog/managed.rs:458-470`）。随后：

- `profiles.is_empty()` 时 `generated_after = None`；非空时才计算 profile hash、加载 base 并生成目录（`managed.rs:499-519`）。
- root `model_catalog_json` 是否绑定 generated path 也完全由 `!profiles.is_empty()` 决定（`managed.rs:521-526`）。
- `sync_current_locked` 只从 SQLite 加载 profiles，再调用上述 prepare/apply；它没有 settings policy 输入（`managed.rs:540-547`）。
- `ManagedCatalogPlan::apply` 再次要求 enabled proxy baseline 与 prepare 时完全一致，否则拒绝提交（`managed.rs:119-165`）。

因此当前状态不是“通用 Codex catalog manager”，而是“代理已应用期间的 managed-profile catalog manager”。PRD R5/R6 会改变这一契约。

#### 3.2 Base catalog 选择和保真能力可复用

当前 base 选择是正确的扩展点：

- 原始 config 有绝对 `model_catalog_json` 时读取完整用户 JSON，并以来源/内容构造 fingerprint（`managed.rs:937-958`）。
- 否则根据当前安装 Codex 的 executable、version、长度和 mtime 构造 fingerprint，再运行受控的 `codex debug models --bundled`（`managed.rs:961-989`）。
- generator 对完整 JSON 做结构化解析，保留顶层与模型未知字段，验证 slug 唯一，再从 visible template clone `aio/*` entries（`managed.rs:1020-1164`）。
- `aio/*` 的窗口只来自 provider capability，并同时写入 `context_window/max_context_window`（`managed.rs:1232-1241`）。372K 策略不得按其 `remote_model_id` 二次覆盖这些 managed entries。

用户原 catalog 文件本身不应写入；只读取它并生成 AIO-owned 完整副本。

#### 3.3 当前 ownership metadata 不足以支持 direct mode

owner key 为 `_aio_managed_model_catalog`，schema 为 v1。metadata 当前包含：

- `payload_sha256`
- `profile_set_sha256`
- `base_catalog_sha256`
- `base_source_fingerprint`
- `managed_aliases`

生成与 hash 见 `managed.rs:1111-1149`，重新验证见 `managed.rs:1276-1322`。它没有以下信息：

- 372K 策略 enabled/disabled；
- 精确目标值 `380928` 与目标 slug 集合；
- 原始 binding 是 absent/bundled 还是用户路径；
- catalog 投影算法版本。

cache reuse 目前只比较 `profile_set_sha256` 和 `base_source_fingerprint`（`managed.rs:502-508`）。如果 profiles 非空时只切换新开关，而不把策略纳入 cache key，会错误复用旧 generated bytes。

#### 3.4 原始 binding 目前只靠 proxy backup

`prepare_catalog_baseline` 从 proxy backup 解析原始 catalog path。若 backup 已指向 AIO generated path，它把这视为污染，并通过删除 `model_catalog_json` 修复（`managed.rs:742-789`）。该修复只能恢复“原本无 binding”的情形，无法重建曾经存在的用户路径。

live binding 只允许等于“baseline 原路径”或“AIO generated path”；第三方改成其他值会 fail closed（`managed.rs:826-840`）。`patch_model_catalog_config` 用 `toml_edit` 只替换/删除根 binding 并做 round-trip 校验（`managed.rs:843-910`）。

当 direct mode 自己合法绑定 generated path 后再启用代理，`backup_for_enable` 会把该 direct config 备份下来。若没有 v2 owner 中的原始 binding，现有污染修复会丢失用户路径。这是代理关闭支持必须先解决的阻塞点。

#### 3.5 现有文件事务安全属性与崩溃缺口

当前 apply 顺序是：

```text
proxy baseline backup -> generated catalog -> live config.toml
```

写失败时反向补偿；显式 rollback 时按 live config、generated、baseline backup 回滚（`managed.rs:168-347`）。每个 rollback 只在当前 bytes 仍等于本事务 after bytes 时恢复，否则返回 recovery-required，避免覆盖外部新写入（`managed.rs:682-717`）。

这对进程内失败注入是可靠的，但“停用并删除最后一个 generated catalog”存在崩溃窗口：现顺序会先删 generated，再恢复 live binding。如果进程在两步之间退出，恢复原始用户 path 所需的 metadata 也可能已消失。新实现必须让提交顺序随方向变化：

- 激活：先写并验证 owner/generated，再写任何指向它的 binding；
- 保持激活但策略变化：原子替换 generated，binding 不变；
- 完全停用：先恢复 live 和 proxy backup 中的原始 binding，最后删除 generated/owner；
- 任一阶段发现 drift：停止并保留可恢复信息。

### 4. 目标语义真值表

代理状态不再决定“是否需要 catalog”，只决定 config 如何投影。catalog 需求必须严格为：

```text
needs_generated_catalog = !profiles.is_empty() || policy.gpt_5_6_372k_enabled
```

| Managed profiles | 372K | Generated catalog | Base 三个 GPT-5.6 | `aio/*` | Effective binding |
| --- | --- | --- | --- | --- | --- |
| 0 | off | 不存在 | 原始 bundled/user 值 | 无 | 恢复用户路径或 absence |
| 0 | on | 存在 | 两个窗口字段均为 `380928` | 无 | 绑定 generated |
| >=1 | off | 存在 | 完全保持 base 值 | 存在，沿用 DB capability | 绑定 generated |
| >=1 | on | 存在 | 两个窗口字段均为 `380928` | 存在且不受策略影响 | 绑定 generated |

上述四行在 proxy enabled/applied、proxy disabled/direct、以及“manifest 仍 enabled 但退出清理已恢复 direct config”三种运行形态下都应成立。

### 5. 建议的核心边界

#### 5.1 使用显式、不可变的 reconcile 输入

prepare/apply 期间不能再次读取可能变化的设置。建议统一入口先在 lifecycle lock 下构造不可变投影：

```rust
pub(crate) struct ManagedCatalogPolicy {
    pub(crate) gpt_5_6_372k_enabled: bool,
}

pub(crate) struct ManagedCatalogInputs {
    pub(crate) profiles: Vec<ManagedCatalogProfile>,
    pub(crate) policy: ManagedCatalogPolicy,
    pub(crate) codex_home_identity: CodexHomeIdentity,
}
```

`prepare` 接受完整 inputs，`apply` 只提交已准备计划并重验快照。profile create/delete/capability update 可在其 DB transaction 中构造“候选 profiles + canonical policy”；startup/proxy/config save 则从已提交 DB + canonical settings 构造 inputs。不要让每个调用者分别猜测开关值或目标常量。

#### 5.2 将 proxy baseline 泛化成配置 ownership context

当前 `PreparedCatalogChange` 强绑定 `CodexProxyBaseline`（`managed.rs:85-104`）。建议改为可表达以下模式的 ownership context：

1. `ProxyApplied`：manifest enabled 且代理投影实际在 live config；用户 direct 基线来自 proxy backup。
2. `Direct`：代理 disabled；live config 是有效 direct config。
3. `ProxyRestoredDirect`：manifest 仍记录 enabled，但网关停止/应用退出后 live 已恢复 direct config。此时不能因为 manifest.enabled 就要求代理 provider 投影仍存在。

逻辑上先恢复“用户原始 config + 原始 catalog binding”，再得到“应用 AIO catalog binding 后的 effective direct config”，最后按模式决定 live 是否还要叠加 proxy provider/auth 投影。proxy backup 应保存可恢复的 effective direct config，使退出/关闭代理后 372K 仍有效；真正的原始 catalog binding 由受 hash 保护的 owner metadata 保存。

#### 5.3 Owner metadata v2

建议保留 owner key、增加显式 v2 reader/writer。v2 至少包含：

```json
{
  "schema_version": 2,
  "managed_by": "aio-coding-hub",
  "projection_sha256": "...",
  "payload_sha256": "...",
  "base_catalog_sha256": "...",
  "base_source_fingerprint": "...",
  "base_binding": { "kind": "bundled" },
  "policies": {
    "gpt_5_6_372k": {
      "enabled": true,
      "tokens": 380928,
      "slugs": ["gpt-5.6-sol", "gpt-5.6-terra", "gpt-5.6-luna"]
    }
  },
  "managed_aliases": []
}
```

用户 catalog 时 `base_binding` 应为带绝对 path 的 tagged value。`projection_sha256` 的规范化输入应覆盖：算法版本、profiles 的全部既有 capability 字段、策略 enabled、精确整数、精确有序 slug 集合、原始 binding 和 base source fingerprint。cache reuse 必须比较 projection hash，而不是继续只比 profile hash。

v1 不能直接按 v2 解释。兼容策略应为：先按旧算法验证 v1；若 enabled proxy baseline 仍能证明原始 binding，则重建为 v2。若只看到 v1 generated binding、没有可恢复 baseline，不得把它猜成 bundled absence，应返回 recovery-required。简单把 `OWNER_SCHEMA_VERSION` 从 1 改成 2 且拒绝所有旧文件，会把正常升级误报成外部篡改，也不合适。

#### 5.4 精确 overlay 算法

在现有完整 base 校验之后、追加 `aio/*` 之前执行 overlay：

1. 只用三个精确 slug 查找，不使用前缀、contains 或裸 `gpt-5.6` alias。
2. generator 现有的全局 slug 唯一性校验继续生效；目标任一缺失时报稳定 typed error。
3. 目标 entry 必须是 object，现有两个窗口字段必须是可接受的非负整数结构；结构异常 fail closed，不静默合成未知 schema。
4. 开启时只替换 `context_window` 与 `max_context_window` 为 JSON integer `380928`。
5. 不触碰 `effective_context_window_percent`、`auto_compact_token_limit`、`comp_hash`、reasoning、priority、visibility 或任意未知字段。
6. 关闭时始终从原始 base 重新派生，而不是尝试把旧 generated 中的 `380928` 猜回 `272000`；用户 base 将来若合法使用其他值，必须原样恢复。

### 6. 专属设置事务

PRD R3 要求专属持久状态，普通 `SettingsUpdate`/`SettingsPatch` 不拥有该字段。可以把字段投影到只读 `SettingsView`，但普通全量保存不能覆盖它。专属 command 的建议流程是：

1. 获取 managed-profile lifecycle lock。
2. 读取 canonical settings、Codex home identity、已提交 profiles、live config、proxy manifest/backup、generated owner 快照。
3. 以目标 enabled 值完整 prepare；包括读取/验证用户 catalog或抓 bundled catalog。此阶段无可见写入。
4. 在 `settings::update` 的写锁内做条件提交：feature 字段仍等于预期前值，并且 Codex home identity 仍等于 prepare 时值。若目标已等于 canonical 值，仍执行幂等 reconcile，但不伪造一次设置变更。
5. 方向感知地 apply catalog/binding 计划。settings 先提交，使进程崩溃后的 startup 能根据持久 intent 收敛；显式调用返回前仍必须完成文件提交。
6. apply 失败时，计划先按 after-bytes 条件回滚文件；随后只 CAS 恢复本 feature 字段，绝不回滚普通 settings writer 的其他字段。
7. 如果 settings rollback 输给并发 winner，重新读取 canonical feature/home，按 winner 再 reconcile；无法证明一致时返回 `SETTINGS_RECOVERY_REQUIRED`，不能返回开关成功。
8. 成功后重新读取 settings、generated owner/hash 和 effective binding，只有三者都与目标一致才返回 confirmed state。

Codex home 竞态要在提交谓词中处理，而不只做 UI disable：

- 普通 settings home mutation 在其 `settings::update` closure 内，若最新 canonical feature 为 true 就拒绝 home 变化；
- toggle commit 要确认 home 自 prepare 后未变化；
- feature 成功关闭且 binding 恢复后，home 变化才重新允许。

这两个条件可覆盖“home 先提交”和“toggle 先提交”两种交错。仅在前端禁用控件或在事务外先读一次 bool 都存在 TOCTOU。

#### 为什么不能复用 settings 的广义 CLI sync

`SettingsRuntimePlan` 当前只有 gateway/home/OAuth mode 变化才触发 CLI proxy sync（`src-tauri/src/app/settings_service.rs:618-735`）。广义 sync 调用 `cli_proxy::sync_enabled` 后：

- partial failure 只记录 warning，返回 `Ok(false)`；
- 顶层 `sync_enabled` error 也被转为 `Ok(false)`；
- 上层只有收到 `Err` 才执行 settings transaction rollback。

证据见 `settings_service.rs:1400-1473,2087-2134`。因此新 feature 不能仅加进 `cli_proxy_sync_required`，而应由专属 command 直接传播 typed catalog error。广义 sync 可以继续用于后台对账，但不能作为开关成功判据。

### 7. 生命周期接线

| 入口 | 当前行为 | 新契约 |
| --- | --- | --- |
| Profile create | lifecycle lock 内 prepare/apply catalog，再提交 SQLite；DB 失败 rollback catalog（`codex_managed_profiles.rs:734-832`） | 候选 profiles 与 canonical policy 一起 prepare；policy on 且首 profile/零 profile切换不能改变 binding 原因判断 |
| Profile delete | lifecycle lock 内先应用移除后的 catalog，再提交 DB；DB 失败 rollback（`codex_managed_profiles.rs:862-950`） | 删除最后 profile但 policy on 时保留 generated/binding；policy off 才完全恢复 |
| Capability update | lifecycle lock 内以候选 capability prepare/apply，DB 失败补偿（`provider_models.rs:1079-1178`） | overlay 只作用 base 三项；`aio/*` 仍严格取 candidate DB capability |
| Proxy enable/rebind | apply proxy 后调用 `sync_current_locked`，失败会回滚 proxy transaction（`cli_proxy/mod.rs:1194-1422`；`cli_proxy/codex.rs:73-215`） | direct config 已绑定 generated 时从 v2 owner恢复原始 base；proxy live 与 effective direct backup 均保持正确 binding |
| Proxy disable | 目前直接 `restore_from_manifest` 并标 disabled（`cli_proxy/mod.rs:1388-1422`） | restore 后在同一 Codex transaction 内按 canonical policy/profiles 重对账；policy需求存在时 direct config仍绑定 generated |
| Gateway/startup sync | 只遍历 enabled manifests；Codex 分支才调 catalog sync（`cli_proxy/mod.rs:1640-1848`；`gateway_service/lifecycle.rs:16-48`） | DB/settings 可用后独立执行 catalog reconcile，不能依赖 gateway 有 base URL 或 manifest enabled |
| Exit/stop restore | `restore_enabled_keep_state` 只恢复备份且保持 manifest enabled（`cli_proxy/mod.rs:1860-1905`；`app/cleanup.rs:147-191`） | 恢复出的 direct config必须继续满足 catalog需求；清理不得把372K binding撤掉 |
| Structured/raw config save | 已持有 lifecycle lock并保存 proxy baseline，再投影 live（`codex_config/mod.rs:293-469`） | active owner 下保存用户其他键时保留 AIO binding；用户明确换 base catalog必须在同一事务重新验证三 slug、更新 owner和generated |
| OAuth-only sync | 当前专门避免 catalog rebuild，并通过 projection 保留 active binding（`cli_proxy/mod.rs:557-577,1473-...`） | 保持 catalog-neutral；只有 feature/profile/base/fingerprint 生命周期事件触发重建 |
| Codex CLI fingerprint变化 | 下次现有 sync 才比较 executable/version/mtime fingerprint | startup 独立 reconcile 必须覆盖；目标缺失或 schema变化时保留旧可恢复 bytes并报告失败，不做部分覆盖 |

所有写入口继续共享 `lock_profile_lifecycle()`。但锁只提供单进程串行化；文件快照、owner hash 和条件 rollback 仍是外部 writer 的必要防线。

### 8. 失败与恢复语义

建议至少区分以下稳定错误类别，便于专属 UI 回到后端确认态：

- base catalog 无效、超过大小限制或 bundled fetch 超时；
- 三个目标 slug 任一缺失/结构非法；
- generated owner/hash 被外部修改；
- live binding、proxy backup、manifest 或 Codex home 自 prepare 后 drift；
- generated、backup、live config 或 settings 任一写入失败；
- rollback 目标已被外部新写入，必须 recovery-required；
- v1 owner 在 direct mode 下无法证明原始 binding。

显式 toggle enable 失败时，持久 intent必须保持/恢复为 false，且 live、backup、generated 保持精确旧状态。后台 startup/fingerprint reconcile 失败时不能擅自把用户 intent改成 false；应保持最后一个已验证目录和 binding、记录 degraded diagnostics，并且不能把当前状态描述为“已应用 380928”。

### 9. 测试矩阵

#### 9.1 核心组合

对 bundled base 和完整用户 base 各跑一次以下矩阵，并在 proxy disabled、proxy enabled/applied 两态重复；退出恢复路径另加 `ProxyRestoredDirect`：

| Profiles | Policy | 必须断言 |
| ---: | --- | --- |
| 0 | off | 无 generated；恢复用户 path/absence；三个目标保持 base |
| 0 | on | 有 generated；恰好三个目标的两个字段均为 `380928`；无 `aio/*` |
| 1+ | off | 有 generated；目标保持 base；`aio/*` capability 正确 |
| 1+ | on | base 三项 overlay 与 `aio/*` 同时正确且互不污染 |

每格都要验证所有非目标模型、顶层未知字段、模型未知字段、95% 字段、注释/TOML 其他根键不变。

#### 9.2 策略、hash 与兼容

- profiles 非空时执行 off -> on -> off，证明每次都重建，不能命中旧 `profile_set_sha256` cache。
- 精确整数为 `380928`；`372000` 只作为负向值，不能被识别为 enabled 或 cache 等价值。
- 裸 `gpt-5.6`、未来 `gpt-5.6-*`、大小写变体不匹配。
- 三个 target 任一缺失、重复、非 object、窗口字段非整数均 fail closed；不得只改找到的两个。
- v1 owner 在有效 proxy baseline 下无损迁移 v2；v1 direct orphan 无法恢复时返回 recovery-required。
- 相同 inputs 重复 reconcile 生成字节稳定；policy、常量、slug、base binding、base content、CLI fingerprint 或 profiles 任一变化都使 projection hash 变化。

#### 9.3 生命周期

- policy on + 0 profile：proxy enable、sync、disable、gateway stop、应用退出、下次 startup 后都保持 direct/proxy effective binding。
- policy off + 1 profile：相同生命周期仍保留 managed catalog；删除最后 profile后才恢复。
- policy on + 删除最后 profile：不得删除 generated；随后关闭 policy 才删除。
- policy off + 创建首 profile，以及 policy on/off + capability update，验证 DB commit失败时 catalog回到精确前态。
- 用户 base path A -> policy on -> proxy enable -> proxy disable -> policy off，最终必须恢复 A，不能变成 absence。
- policy on 时 Codex home mode/override 的后端 mutation被拒；关闭并完成恢复后 home rebind成功。
- Codex executable/version/mtime变化触发 bundled重抓；新 catalog缺 target 时不覆盖最后已验证目录。
- OAuth-only mode改变不增加 catalog fetch/rebuild计数，但 active binding保持。

#### 9.4 事务失败注入与并发

- prepare 阶段：用户 catalog read、bundled spawn/timeout/JSON validate失败时零写入。
- settings commit失败：零文件写入。
- owner/generated、proxy backup、live config各提交点失败：已写阶段按条件逆序恢复。
- 完全停用在 live恢复后崩溃/失败：generated仍在，可由 startup清理；不得出现 binding指向已删除文件。
- settings回滚时普通 writer同时修改无关字段：只恢复 feature字段，不覆盖 winner。
- home变化与 toggle enable 两种确定性交错都不能跨 home留下 generated binding。
- 外部在 prepare/apply间改 live、backup、generated或用户 catalog：拒绝覆盖。
- 外部在 apply后、rollback前改任一目标：返回 recovery-required，不覆盖外部新 bytes。
- 两个共享 `CODEX_HOME` 的进程竞争：测试至少证明 owner/snapshot mismatch fail closed；不能宣称进程内 mutex提供跨进程互斥。

#### 9.5 真实 Codex 0.147.0 集成

在隔离 `CODEX_HOME` 中绑定 generated catalog，启动新的 Codex 进程并读取非 `--bundled` 模型列表，断言三个名义字段为 `380928`；关闭后新进程回到 base 值。`--bundled` 只可用于验证来源，不可用于证明 custom catalog 已加载。已运行 Codex 进程不要求热更新。

### 11. Code Patterns

- **Prepare/apply/rollback token**：先快照和构造计划，apply 前复验，返回可条件 rollback token；见 `managed.rs:119-347`。
- **外部漂移 fail closed**：rollback 只覆盖仍等于 after-state 的文件；见 `managed.rs:682-717`。
- **完整 JSON 结构化派生**：保留 base 与未知字段，只追加 owned entries；见 `managed.rs:1020-1164`。
- **原 binding / generated 二选一验证**：第三路径被视为外部 drift；见 `managed.rs:826-840`。
- **active binding 穿透代理投影**：raw/structured 保存根据当前 binding 保留 generated path；见 `managed.rs:550-563`、`cli_proxy/mod.rs:557-577`。
- **DB 最后提交并补偿文件**：profile/capability mutation 先应用候选 catalog，SQLite失败后使用 applied token rollback；见 `codex_managed_profiles.rs:734-950`、`provider_models.rs:1079-1178`。
- **settings owned-field CAS**：rollback 比较 committed token，输给并发 winner 后重读 canonical runtime；见 `settings_service.rs:1217-1397`。专属 toggle 应复用“只回滚自己字段”的思想，而不是加入普通 owned token。
- **部分失败只做状态结果**：`sync_enabled` 聚合 per-CLI result，settings wrapper 把失败变为 `Ok(false)`；见 `cli_proxy/mod.rs:1640-1848`、`settings_service.rs:1400-1473`。

## Caveats / Not Found

- 官方 Models 页面确认 slug，但没有公开“372K”或 `380928` 的上游产品承诺；`372 * 1024` 是本任务明确选择的产品值。权威 0.147.0 bundled 数值来自固定 OpenAI source tag。
- 0.147.0 保留 95% 有效窗口后，名义 `380928` 的有效预算是 `361881`。这不是实现误差；本任务明确禁止把 percentage 改为 100。
- 现有代码没有 proxy-disabled catalog owner/sidecar，也没有可直接复用的原始 binding journal。v2 generated metadata加方向感知提交可满足正常恢复；若实现无法保证删除顺序，则必须增加独立 journal。
- 当前 lifecycle mutex 仅进程内有效。桌面 single-instance 降低普通双开概率，但开发版、portable 或其他 AIO 进程仍可能共享 `CODEX_HOME`；跨进程只能依靠快照/hash fail closed，除非另增 OS 文件锁。
- WSL Codex 配置当前不参与 Windows generated catalog 生命周期；本报告不把 Windows路径投影到 WSL，也不声称覆盖 WSL 372K。
- 后台 startup/CLI fingerprint reconcile 失败时，现有 settings view 没有“intent=true 但 applied=false”的诊断字段。若产品要求 UI 精确呈现降级态，需要增加独立 status DTO；仅显示持久 bool 会把后续漂移误报成已生效。
