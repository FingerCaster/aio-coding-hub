# 修复供应商删除残留并增强决策链展示

## Goal

保证供应商配置被删除后，所有调用顺序中的对应引用同步清理；同时让请求日志详情的决策链能够直观、唯一地识别供应商，而不是只显示难以辨认的 ID。

## Background

- SQLite 已通过 `ON DELETE CASCADE` 清除三类顺序表中的 provider 引用，且应用服务会清理网关运行时路由；残留来自删除 mutation 未同步处理 Default 与排序模板 Query 缓存，以及删除前在途查询可能回写旧快照。
- 请求日志的 attempt 历史快照已经保存 `provider_name`、`provider_id` 和 `base_url`，但决策链卡片正文只渲染 ID。名称和 ID 已能在不回查当前 provider 表的前提下唯一、直观地展示历史身份。
- 工作必须在独立 Orca worktree 和独立分支内完成，不得合并到 `main`。

## Requirements

- 删除任意供应商配置成功时，前端必须立即从供应商列表、Default 调用顺序及该 CLI 所有已缓存排序模板中移除对应引用，并与持久化真值重新对账。
- 删除前已启动的供应商/调用顺序查询不得在稍后完成时恢复被删除 provider；刷新或重启后也不得重新出现。
- 清理不能误删其他供应商，包括共享相同域名、类型或相似名称的配置。
- 请求日志详情中每个决策链 attempt 的折叠态和展开态都必须显示“请求时名称 + 稳定 ID”；起始/最终摘要使用相同格式，确保同名或同域名配置可区分。
- 历史日志引用已删除 provider 时继续展示请求时的名称快照和 ID；名称缺失、空白或为既有 unknown 哨兵时回退为“未知供应商 (#ID)”，不能回查并误映射到其他供应商。
- 不改变路由选择、调用顺序执行语义、日志持久化语义及凭据安全边界。
- 为两项修复补充覆盖正常、重复/共享属性以及缺失供应商场景的自动化测试。
- 完成仓库要求的相关测试、类型检查、lint、Rust 检查和生成绑定校验，并成功产出 Windows MSI 安装包。

## Acceptance Criteria

- [x] 删除位于 Default 和一个或多个排序模板中的供应商后，所有已缓存对应引用立即消失，删除前在途查询不能恢复它，持久化三类顺序表中也不再包含其 ID。
- [x] 仅按稳定供应商 ID 清理；同域名、同类型或同名的其他供应商及其顺序项保持不变。
- [x] 请求日志详情的每个 attempt 及起始/最终摘要同时提供可读名称和稳定 ID；同名或同域名配置仍能被明确区分。
- [x] 历史日志中的已删除 provider 使用历史名称快照；名称未知或 ID 无效时采用明确且不崩溃的回退标签。
- [x] 两项行为均有回归测试，且相关现有测试、全量质量门禁全部通过。
- [x] Windows MSI 构建成功，安装包路径、文件名、大小和校验摘要可报告。
- [ ] 所有提交仅存在于 `FingerCaster/fix-provider-delete-log-display`（或该独立 worktree 的后续任务分支），未合并到 `main`。

## Out Of Scope

- 不调整供应商路由算法、故障转移优先级或请求日志采集范围。
- 不新增供应商重命名、批量删除或日志迁移功能。
- 不创建、合并或推送 PR，除非用户后续明确授权。
