# Codex 可自定义模型上下文规则

## Goal

将已发布的 GPT-5.6 372K 专用开关扩展为设备本地的 Codex 模型上下文规则管理功能。用户可以为指定 Codex 模型配置名义上下文窗口，不再受限于 `gpt-5.6-sol`、`gpt-5.6-terra`、`gpt-5.6-luna` 和固定 `372000`。

## Background

- 现有功能以 `AppSettings.codex_gpt56_372k_context_enabled: bool` 持久化，并通过专用 IPC 原子切换。
- `ManagedCatalogPolicy` 当前只携带该布尔值；目录生成器硬编码三个精确 slug，并把每个目标的 `context_window` 与 `max_context_window` 同时改为十进制 `372000`。
- 已有 managed catalog 管线负责读取 Codex bundled catalog 或用户绝对目录、保留未知字段、写入 ownership metadata、绑定 `model_catalog_json`，并对配置、生成目录和代理备份执行条件回滚。
- 当前 `CodexModelCatalogState.models` 可向前端提供已安装 Codex 暴露的精确 `model` ID、显示名和推理能力，但不包含原始 `context_window` 或 `max_context_window`。
- 现有策略是 Codex home/设备拥有的本地策略，不随便携配置导入导出迁移；启用时阻止切换 Codex home，且只对新启动的 Codex 会话生效。

## Requirements

- R1. 用可持久化的规则集合替代硬编码的 GPT-5.6 372K 策略；每条规则表达一个精确目标模型 ID 和一个十进制名义上下文 token 值。
- R2. 规则只派生 AIO 拥有的完整 model catalog，不修改 Codex 安装目录，也不使用顶层 `model_context_window` 冒充逐模型目录能力。
- R3. 每条规则只维护一个上下文 token 值。应用规则时将该值同时写入目标条目的 `context_window` 与 `max_context_window`；不允许分别配置两个字段，`effective_context_window_percent`、自动压缩阈值、推理能力和未知字段继续由基础目录拥有。
- R4. 保留现有事务语义：准备阶段无副作用，提交前重检所有权与漂移，失败时条件回滚所有已提交目标，并在无法恢复时返回 typed recovery-required 错误。
- R5. 没有规则且没有 managed Profile 时，恢复用户原始 `model_catalog_json` 绑定或 bundled 默认，并只删除 AIO 拥有的生成文件；仍有 managed Profile 时，仅撤销规则改写。
- R6. 规则更新、Codex home 选择、structured/raw config 保存、配置导入、代理启停、启动恢复、Profile 和 provider capability 更新必须共享同一 policy-aware reconciliation 路径。
- R7. 旧版 `codex_gpt56_372k_context_enabled=true` 必须有确定、无数据损失的迁移语义；旧开关不能与新规则形成两个独立真源。
- R8. UI 必须支持查看、添加、编辑、启停和删除规则，阻止重复提交，并在后端确认后才展示成功状态。
- R9. 每条规则只匹配一个非空的精确 Codex 模型 ID。禁止前缀、通配符、正则或隐式模型族匹配；同一精确 ID 不得出现多条规则。
- R10. 继续采用 Codex 上游 JSON 的十进制 token 数值口径，例如 `272K = 272000`、`372K = 372000`。
- R11. 规则的静态校验、基础目录目标校验和生命周期失败必须返回稳定 typed error；错误不得依赖前端解析英文消息，也不得回显完整目录、无界模型列表或敏感绝对路径。
- R12. 添加规则时，前端提供当前 Codex 目录中可见模型的可搜索建议，同时允许手工输入精确模型 ID。建议列表不是真源；后端必须以本次事务读取并验证的基础完整目录为权威。
- R13. 保存或启用规则集合时，所有启用规则必须在同一份经验证的基础完整目录中各自命中恰好一个条目。任一目标缺失、重复或结构无效时，整次规则/目录事务在首次写入前失败并保留旧 canonical 状态；禁止部分应用或未来自动激活。
- R14. 每条规则持久化独立 `enabled` 状态，用户可暂停后再恢复；不提供额外的规则集全局总开关。模型 ID 在启用与禁用规则之间也必须全局唯一，删除是独立且显式的操作。
- R15. 禁用规则仍须通过模型 ID 格式、全局唯一性和 token 数值边界校验，但不要求目标存在于当前基础目录。禁用规则不参与目录派生、不会自动激活；重新启用时按 R13 执行完整原子验证。
- R16. 上下文 token 值必须是 `1,024..=10,000,000` 的十进制整数，复用现有 Provider 模型能力与 CX2CC 的跨层常量；前后端不得维护另一套边界。
- R17. 规则集合最多 `128` 条；规范化模型 ID 先去除首尾空白，按区分大小写的精确字节匹配，必须为 `1..=256` 个 UTF-8 字节且不含控制字符。canonical 存储按模型 ID 确定性排序，不提供排序或优先级 UI。
- R18. 规则不得以 `aio/` 开头。`aio/*` managed Profile 的上下文继续由 provider-model capability 独占并投影到目录，通用规则不能成为第二真源。
- R19. 从旧 settings schema 升级时，`codex_gpt56_372k_context_enabled=false` 迁移为空规则集；`true` 迁移为 `gpt-5.6-sol`、`gpt-5.6-terra`、`gpt-5.6-luna` 三条启用规则，每条 token 值为十进制 `372000`。迁移必须幂等，canonical 新 schema 不再保留独立旧开关真源。
- R20. 规则集合继续是设备/Codex-home 本地策略。便携配置导出不包含规则，配置导入忽略任何同名输入并保留导入前 canonical 规则；导入不得隐式启用、禁用、添加、删除或修改规则。
- R21. 前端在本地草稿中完成规则新增、编辑、启停和删除；只有显式“应用更改”提交整个规范化集合。后端只提供整集合原子替换语义，不提供会产生中间状态的逐字段写接口。取消、校验失败、提交失败或 canonical 确认失败均回到最后确认状态。
- R22. 规则目标可在 R16 的全局边界内高于、等于或低于基础目录值。UI 在基础值可读时显示“基础值 -> 目标值”；提高值时显示非阻塞风险提示，明确目录声明不会增加模型/provider 的真实能力。不得修改 Codex 的 `effective_context_window_percent` 或自动压缩语义。
- R23. 通用规则 UI 保留“添加 GPT-5.6 372K 预设”快捷操作。该操作只向当前前端草稿加入 `gpt-5.6-sol`、`gpt-5.6-terra`、`gpt-5.6-luna` 三条启用的 `372000` 规则，并复用普通草稿的重复检测、编辑与整批提交；后端不得保留模型族、版本号或 `372000` 的特殊策略。
- R24. 已成功提交的启用规则后来因 Codex CLI/基础目录升级而目标缺失、重复或结构不兼容时，保留 canonical 启用意图、最后一次成功生成的目录与现有绑定，并以可重试的 typed 状态阻止启动继续；不得自动删除、禁用规则或部分重建目录。用户可显式禁用、修正或删除问题规则；若同一精确 ID 后续重新出现在兼容基础目录中，则下次启动或显式重试按持久意图自动恢复收敛。该行为只适用于先前已成功提交的规则，不改变 R13 对新候选整批拒绝且不得未来自动激活的要求。

## Acceptance Criteria

- [ ] 用户可新增至少一条“模型 -> 上下文 token 数”规则，并在保存后从 canonical backend 状态重新读取。
- [ ] 新启动的 Codex 从 AIO 派生目录读取规则值；每个命中模型的 `context_window` 与 `max_context_window` 都等于该规则的唯一 token 值，非目标条目与未知字段保持原样。
- [ ] 多条合法规则可同时生效，规则增删改能够原子收敛到一个确定目录；无部分成功或静默丢规则。
- [ ] 任一启用规则目标在基础目录中缺失时，规则设置、生成目录、live config 和 proxy backup 均保持提交前状态；后续 Codex 升级不会令被拒绝的规则自行出现或激活。
- [ ] 仅精确模型 ID 能命中目录条目；前缀、通配符和正则文本不展开，同一精确 ID 的重复规则在任何文件/设置提交前被拒绝，并给出稳定错误码。
- [ ] 基础目录、生成目录、live config 或 proxy backup 在 prepare 后漂移时 fail closed；注入任一提交/确认失败后能恢复规则设置和所有仍归本事务拥有的文件。
- [ ] 旧 372K 开关升级后得到产品决策规定的等价规则状态，升级与重复启动均幂等。
- [ ] structured/raw config、配置导入、Codex home 切换、代理启停、启动恢复及 managed Profile 共存场景均有回归测试。
- [ ] 前端覆盖添加、编辑、启停、删除、验证错误、保存中禁用、失败回读和新会话生效提示。
- [ ] 模型输入既能从当前目录建议中选择，也能手工输入；两条路径提交同一规范化精确 ID，并由后端目录校验决定是否可应用。
- [ ] 单条规则可在不删除模型 ID 和 token 值的前提下启停；没有启用规则时不再因规则集合单独维持生成目录，且不存在第二个全局开关真源。
- [ ] 模型暂时下线后，其禁用规则仍可读取、编辑和删除并显示不可用状态；它不阻塞启动恢复，也不会在模型重新出现时自行启用。
- [ ] `1,024` 与 `10,000,000` 可保存，越界值、非整数、非安全整数和空 token 值在前后端均被拒绝，且边界常量有跨层漂移测试。
- [ ] 第 128 条规则可保存，第 129 条、超长/控制字符模型 ID 和任意 `aio/*` 目标在首次写入前被拒绝；不同排列的同一规则集合生成相同 canonical bytes 与 owner hash。
- [ ] 旧开关关闭/开启两种 schema 64 设置分别迁移为空集合/三条精确 372000 启用规则，重复加载不重复添加或改变规则。
- [ ] 配置导出不泄露规则；导入含空、不同或恶意规则载荷时仍保留设备原规则，并继续遵守 Codex-home rebind 与 catalog 补偿顺序。
- [ ] 多项草稿改动只触发一次后端规则事务和一次 catalog 重建；取消不发写请求，失败后 UI 从 canonical 查询回读且不保留伪成功草稿。
- [ ] 高于和低于基础值的规则都能原子应用；提高值有可访问的风险提示，基础值未知时仍允许手工规则但不伪造比较值。
- [ ] “添加 GPT-5.6 372K 预设”只改变未提交草稿；已有任一同 ID 规则时不制造重复项并给出明确反馈，用户仍须点击“应用更改”才触发一次通用规则事务。
- [ ] 已生效规则因 CLI 升级失配时，canonical 启用状态、最后成功目录、live config 和 proxy backup 保持不变，启动停在可重试失败态并可从设置修复；兼容目标恢复后，显式重试或后续启动能按原启用意图自动收敛。此前因目标缺失而被拒绝的新候选不会因此自动出现或激活。
- [ ] 生成 bindings、前端测试、Rust 定向与全量测试、lint、typecheck、fmt、clippy/check 和 Linux CI 全部通过。

## Out Of Scope

- 修改 Codex 自身的 95% 有效窗口安全系数或自动压缩算法。
- 修改 Codex 安装包内的 bundled catalog 文件。
- 在当前任务中为 Claude、Gemini 或其他 CLI 建立同类规则系统。
- 未经单独产品决策修改 `aio/*` managed Profile 的 provider capability 权威关系。
