# Pi / OMP 接入实施计划

## 状态与执行原则

本文件最初为 planning 阶段的实施安排。用户于 2026-09-26 明确要求“开始吧”，任务现已进入 in_progress。W0–W7 是同一首期交付的内部工作包，不代表将网关延期；实际运行证据与未完成项分别记录在 research 下，不把计划条目视为已经通过。

开始条件已满足：用户评审 [需求](prd.md) 与 [设计](design.md) 后明确要求实施；基线及工作区已确认，任务已按 Trellis 启动。真实 CLI 实验使用隔离 HOME / 配置目录和固定版本，不升级用户全局安装、不读取真实凭证、不连接计费上游。

自动上下文注入存在单文件 32,768 字节上限。gateway-failover-route-contract.md 和 codex-managed-model-route-contract.md 超过此限，实施和检查者必须主动分段读取完整文件，不能仅依赖注入片段；原规范仍是权威来源。

## W0：真实 CLI 契约验证与夹具

目的：在大范围业务修改前验证设计依赖的请求形状及配置解析契约。

1. 基于 [固定来源](research/source-baselines.md) 构建隔离运行脚本，禁用扩展、项目配置及真实环境凭证干扰，仅提供假密钥和本地模拟服务。
2. 为 Pi / OMP 各运行四种目标协议，捕获路径、请求 headers、模型 ID、流式与非流式请求。验证 baseUrl 是否包含版本前缀以及 SDK 的最终 URL，尤其是 Google。
3. 按协议能力覆盖工具调用、思考、图像、取消、结束及错误事件；记录 CLI 内部重试与 AIO attempt 预算叠加的行为。
4. 固化 Pi JSONC 的真实语法边界、OMP YAML / profile / 环境目录优先级、旧 JSON 的只读提示行为。证明解析器不把损坏文件当成空配置。
5. 输出不含密钥的夹具、版本矩阵及可复现命令。若来源与实际行为不一致，修订设计证据并解决差异，不静默减少两个 CLI × 四种协议的首期范围。

出口：真实客户端协议和文件契约可复现，避免后续使用“看起来兼容”的假设。对应 A02、A06、A10、A12 的基础证据。

## W1：身份、目标与原生存储基础

1. 扩展前后端 Pi / OMP typed identity 和能力注册项；尚未完成的能力不提前打开。
2. 建立 native domain 与两个独立 infra 适配器，统一目标 ID、目录解析、节点读写结果及可恢复错误。
3. 增量数据库迁移保存原生归档和目标归属；AppSettings 使用独立字段，遵守字段所有权与回滚契约。
4. 实现最新文档读取、内容 revision、进程内互斥、原子替换、私有原始备份和条件补偿；明确外部写入者不参与锁时的剩余竞争窗口。
5. 对坏文件、未知字段、重复 YAML key、别名 / merge 语义歧义、路径混淆及外部修改构造测试；不能支持无损修改的输入进入明确只读状态。

出口：原生存储可安全定位、读取和修改单个节点。对应 A01–A05、A10 的基础层。

## W2：原生供应商与模型管理

1. 实现目标列表 / 验证、供应商列表与编辑读取、保存 / 应用 / 移除 / 删除归档命令及生成的类型绑定。
2. 在 Pi / OMP 原生视图复用现有表单与视觉习惯，分别承载原生模型、覆盖项和能力；列表不展开庞大模型目录。
3. query key 带目标身份和版本，切换目标、刷新及预览后确认均检查陈旧状态；显式节点存在是启用事实。
4. 外部刷新只更新原生归档，不暗改网关上游快照。区分原生节点、AIO 生成节点和停用归档，托管字段修改走对应生命周期。
5. 展示 CLI 路径 / 版本探测及能力边界，不把只读探测包装成安装更新功能；共享暂不完整时明确禁用。

出口：原生管理完整可用且保留原生语义。对应 A01–A05、A10、A14。

## W3：网关协议维度与公共执行链

1. 新增请求上下文中的 WireProtocol，保留真实 source_cli_key。为 Pi / OMP 增加设计中的显式协议路由，既有路由入口保持兼容。
2. 分离协议相关的认证、请求模型读取、上游 URL、SSE / 非流式处理、用量及错误编码；沿用共同的 attempt、deadline、取消和提交边界。
3. 客户端专属处理仍以客户端 / 能力选择，不能仅因协议相同而为 Pi / OMP 开启 Codex 或 Claude 专用行为。
4. 覆盖 Grok 两种协议与旧四 CLI 行为；不要建立另一套独立重试、熔断或统计实现。
5. 将 W0 的夹具接入真实 AIO 网关测试，特别验证流中错误、取消、缓冲及提交后不重试。

出口：两个新客户端的四协议经过现有公共执行链。对应 A06、A08 的传输部分、A11–A13。

## W4：AIO 上游池、显式导入与模型目录

1. 为新客户端上游记录协议，并保存网关所需的显式模型能力元数据；旧客户端与 Codex 模型目录不强行迁移到新结构。
2. 实现原生 → 网关导入预览：展示模型级协议 / URL / headers 覆盖并按可表达的连接条件分组；无法忠实转换的项拒绝导入或要求用户明确补全。
3. 网关凭证在 AIO 中明确配置；原生值中的动态表达式不执行，不能把表达式文本当成可用 API key。
4. 形成可发布目录：仅使用已知元数据；多个上游的同协议同名模型取可证明的能力交集、容量下限，缺失能力不能按名称猜测。
5. 路由候选限定同客户端、协议、已声明模型且覆盖已发布能力快照；复用既有模型映射归属与门控，排除不兼容项不计 attempt 或健康惩罚。目录待更新时不得自动加入能力更弱的新上游。
6. 补齐删除、缓存和目录失效处理；共享若启用，先完善新字段契约及往返校验。

出口：原生归档和网关快照相互独立；同协议模型可复用现有失败切换。对应 A04、A06–A08、A11、A13–A14。

## W5：独立 AIO 入口发布与撤回

1. 一个网关管理视图管理至多四个协议节点；模型目录来自 W4，采用白名单生成字段。
2. 预览显示目标、原生 key、协议、URL、模型及差异；监听器和有效候选就绪后才应用可用入口。
3. 执行分阶段 generation：数据库意图、原生节点写入、所有权 manifest 和状态确认；跨文件 / 数据库失败按 revision 及 digest 条件补偿。
4. 检查同名非托管节点、手工修改、端口变化、重复应用、部分成功和撤回；不能覆盖冲突节点或整份配置还原。
5. 保持原生默认和现有会话不变；提示用户在原生 CLI 选择 AIO 模型，状态分别表达节点存在、监听器及已观察流量。

出口：独立入口安全共存，可定位失败并恢复。对应 A08–A10、A14。

## W6：端到端验收与回归矩阵

- 真实固定版本 Pi / OMP × 四协议，从 CLI 经 AIO 到本地模拟上游；记录可复现命令、版本及脱敏请求 / 事件证据。
- 每种协议至少两上游覆盖可重试失败和成功切换；跨协议或未声明模型的候选不得出站。
- 原生直连与 AIO 入口共存，切换目标 / profile 不串写；覆盖 YAML / JSONC、旧格式、外部修改和每个持久化阶段的故障注入。
- 覆盖正常与异常 SSE、非流式、工具 / 图像 / 思考能力、取消、提交前后失败；对账请求、attempt、模型、用量、缓存与价格。
- 比对 AIO 管理操作前后测试夹具中的认证文件、SQLite 数据库和默认设置内容及 mtime；真实 CLI 自身的状态写入另行观测，不能混算成 AIO 改写。证明动态命令不执行、敏感数据不进入日志 / 导出。
- Windows 运行测试；对实际声称支持的 macOS / Linux 平台补路径和权限证据。回归旧四 CLI，特别是 Grok 双协议和 Codex 受管模型。

出口：PRD A01–A14 每项均有证据。不能以单元测试替代真实 CLI 协议验证，也不能把测试夹具的直接调用冒充真实 CLI 流量。
